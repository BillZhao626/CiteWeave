# v0.2 Technical Foundation

Status: **ACCEPTED — Human Review incorporated** · 2026-09-27

这是已接受的责任与选型方向，不是已接受的 Architecture Design、Feature Spec、Evaluation Spec 或 ADR。不定义表、字段、路由、事件格式或新运行时。接受记录见 [Blueprint](V02_BLUEPRINT.md) 与 [PR #1](https://github.com/BillZhao626/CiteWeave/pull/1)。已实现职责以 [ARCHITECTURE](ARCHITECTURE.md) 为准。

持久信任原则：Conversation memory 是上下文状态，不是 documentary Evidence。历史 assistant 回答、摘要、推断实体与 memory item 可以帮助理解意图、指代、有效约束和话题变化，但不能无有效原文 Evidence 而成为技术事实依据。Relevance first, Recency second 不冻结具体评分公式，也不要求新的数据库或服务；相关 ADR 仍只是候选。

## 保留的基础与重新评估条件

| 决策方向 | 解决的问题 / 为什么适合 | 暂不选择的主要替代 | 重新评估触发条件 |
| --- | --- | --- | --- |
| PostgreSQL 继续作为持久业务权威 | 文档、Run / Job 已在此维护；会话中需跨刷新 / 重启的内容、状态身份及其关联应有相同持久归属 | 浏览器或 Redis 唯一保存会话会丢失服务端一致性；再加独立记忆数据库增加运维与双写问题 | 有实际负载 / 事务证据证明当前方案不能满足已接受需求；先分析访问模式 |
| Redis 维持 recoverable broker | 现有 Celery 通知传输；队列丢失不能改变业务真相 | 不因 Memory 一词把 Redis 变成摘要 / 会话唯一数据库；不引入未经证明的通用缓存 | 经测量存在可观重复读取或传输瓶颈，并先规定失效与恢复语义 |
| Celery 维持异步任务执行 | 长耗时摄取已有 worker 边界、PG 状态与 stale-attempt fencing | 不把每次对话或摘要自动拆成新异步任务；不引入第二任务框架 | 摘要等任务实际需要后台完成且有可接受的延迟 / 一致性目标，再审阅重试、取消、幂等与恢复 |
| Qdrant 与现有检索链保留 | Dense + BM25 + RRF + BGE、Parent / Child 和 EvidencePack 已有契约与回归面 | 不以升级产品版本为理由换向量库、embedding、reranker 或排名语义 | 控制评测定位到现有召回 / 精排的具体不足，且收益覆盖重建、迁移与回归代价 |
| 会话持久化由后端定义权威 | 刷新、断线、失败恢复与 Run 关联不能依赖 UI 缓存 | 前端全量历史当作真相、只保留最后一份摘要、覆盖旧状态均不足以解释历史回答 | Architecture Design 发现数据保留 / 删除、并发编辑或可恢复性需求变化 |
| Session memory 先用最小可验证选择机制 | 保存可定位的历史，按语义 / 实体 / 任务相关性选择；近期窗口只是一种输入 | 不立即建设第二套向量索引、跨会话用户画像或把全部历史灌入 prompt | 在有界候选选择的 dev 对照中持续漏掉旧而相关历史，才比较稀疏 / 向量召回；如用 Qdrant，仍须隔离授权、可重建和发布语义 |
| Summary / compaction 是有损派生视图 | 长会话需要有界上下文；保留原始来源关联及版本才能解释遗漏和错误 | 摘要不能覆盖唯一历史、变成事实证据或未经验证写回用户意图 | 经评测出现实体、否定、范围或时间丢失；重审摘要触发、保留、重建和选择策略 |
| 保留现有模型适配与 profile 身份 | DeepSeek 生成、E5 / BGE 有既有边界；新行为必须可比较、可追溯 | 不预设更大模型、多模型串行调用、Agent framework 或 prompt-only 解决所有行为 | 人工评测证明当前模型 / 确定性方案达不到预注册目标，且费用、延迟、失败率允许替代 |
| 后端控制策略，前端控制交互 | FastAPI 执行授权、状态、上下文预算、改写与最终引用验证；React 展示会话、草稿 / 最终区别与诊断入口 | 不在 UI 独立决定检索范围或可信最终答案；不让前后端维护两套手写 API 类型 | 新用户场景证明需要离线客户端能力时另行审阅；继续从 Pydantic / OpenAPI 生成类型 |
| LocalBlobStore 与不可变证据保留 | 原始 PDF、canonical bytes 与 span 身份已经支撑引用 | 不因为会话增加云对象存储，也不复制 PDF 作为记忆 | 明确的部署需求、数据量与恢复证据推动独立迁移评审 |

这些方向不构成性能、容量或故障恢复已通过的声明。当前离线 CI 与完整 Windows 运行验证范围见 [QUICKSTART](QUICKSTART.md)。

## 必须在架构阶段回答的边界

- Conversation、Turn、Run 与不可变状态快照如何关联；重复请求、并发轮次、SSE 断线、取消和 provider 不确定结果如何收敛为一次有效结果。
- 会话授权、知识库 / 文档范围变化、保留和删除的语义；历史能否回看与当前可否取用证据必须分开。
- Working Memory / Summary 的可信级别、来源关联、写入时点、损坏后的重建，以及是否需要异步工作。PG 权威不等于在本轮冻结事务方案。
- Recent Turns、相关历史、证据与回答各自的上下文预算；超预算、歧义、无证据、旧历史矛盾时的用户行为和 fallback。
- 决策次序、是否合并 Topic Shift / Coreference / Rewrite、模型调用次数与 trace 的可重放范围。可检查是记录决策输入与结果，不要求暴露模型私有思维链。
- 新数据的 Alembic 升级、兼容、恢复与删除测试；实际字段、API、SSE 事件及 UI 操作留给 Architecture / Feature Spec。

## 候选 ADR（本轮不创建）

| 候选 | 值得长期记录的原因 | 审阅时需比较 / 迁移影响 |
| --- | --- | --- |
| 会话状态权威及有效轮次提交 | 影响刷新、重试、取消、旧 Run 的解释 | PG 事务 / 派生状态 / 同步与异步；新持久数据和旧 Run 兼容 |
| 记忆与文档证据的信任及范围边界 | 防止历史回答、摘要与 prompt 注入升级成权威 | 原历史、摘要、选中记忆、原文证据的权限与身份；保留 / 删除影响 |
| 有界上下文、摘要与相关历史选择契约 | 影响每次生成可用信息及重放 | 简单候选选择、稀疏 / 向量召回、摘要策略；派生数据版本与重建 |
| 对话 profile / trace 的版本语义 | 不能用新策略重解释旧会话运行结果 | 运行配置快照、版本选择与旧 Run 展示；是否需迁移由设计确认 |

候选可能合并或取消。只有方案及备选、后果、迁移影响和 Human Review 接受记录齐备，才产生 Accepted ADR；不要用 ADR 固化尚未验证的详细算法。
