# ADR0024 — operational Trace and read-only recovery inspection

Status: Owner-authorized M2 implementation; candidate for Human Implementation Review, not independently marked ACCEPTED. 2026-10-03.

The Owner's M2 mission authorizes this increment on `18caafbb0f43d9b1c0cb851002412e7058893660` and supersedes the earlier M1 stop-before-M2 navigation. PostgreSQL remains the business authority. Extend `cw5_run_events` and the authenticated Conversation Trace instead of installing a monitoring platform or another event store. Query dispatch, retry classification and Acceptance authority remain those of ADR0023.

Alembic0014 adds nullable `phase` and `current_fence` to existing immutable events. No backfill/default or historic migration edit. `phase` identifies local workflow/provider purpose; `current_fence` records the Conversation fence observed by a local stage or the fence which terminal bookkeeping advances. New local stage start/completion/failure and stale-result rejection kinds are append-only facts. Old events retain nulls. A stale worker can append one rejection diagnostic per Run/current-fence under the Conversation lock, without changing Run, provider accounting, head or Acceptance.

Measure local stages with a monotonic clock. Persist successful publication timing inside the Acceptance transaction before its last guarded flush, so diagnostic write failure cannot leave a separately committed result misrepresented as failed. That duration excludes the final flush and commit acknowledgement. A started stage with no completion is incomplete. Known local completion after cancellation describes local work only; the separate CANCELLED Run/result authority remains unchanged. Stage recording verifies scoped Run identity under the Conversation lock; it does not add live-status/deadline gates. Existing workflow/ledger/publication guards retain execution authority. Stage-recording database failures propagate, with no retry or suppressed database error. Only actual stale_owner/run_not_active conflicts append runtime stale rejection facts.

The bounded projection reads the newest64 events ordered by `(created_at,id)` and the existing two product provider purposes. UUID tie-breaking is deterministic, not evidence of causal order between simultaneous timestamps. Missing timestamps, usage, attempts and estimates remain absent. Reversed DB timestamp intervals remain unavailable/incomplete rather than measured zero. A provider total with missing attempt measurements remains incomplete even if the latest ledger state is COMPLETED. Provider markers precede I/O: a DISPATCHED/UNKNOWN row proves a committed dispatch marker, not that bytes definitely reached a provider. Known HTTP responses/completed observations provide stronger evidence. Receipt costs remain pinned estimates, never bills. The error taxonomy is a projection and cannot grant retry authority.

Operator inspection uses the existing local CLI with `--inspect`, explicit workspace and optional Run identity. A PostgreSQL REPEATABLE READ READ ONLY transaction provides a coherent bounded snapshot. Inspection predicts M1 reconciliation from existing phase facts but does not modify them, dispatch, retry or schedule. Apply reconciliation only through the existing separate mutating CLI invocation. Selection can become stale after inspection; locked reconciliation rechecks durable truth.

Alternatives: log-only spans disappear on restart; a second event table duplicates durable authority; automatic restart retries violate UNKNOWN; an admin HTTP API would add authentication/authorization surface without a present need. Prometheus/Grafana/OpenTelemetry infrastructure and query Redis/Celery insertion are outside this milestone. Reconstructing raw provider outputs remains deferred because it changes privacy/validation obligations.

Migration impact: additive nullable columns, preserved event retention triggers and existing M1 publication constraints; fresh/populated/repeated isolated upgrades tested. Downgrade refuses deletion of durable observability facts; use fix-forward. Application database upgrade/deployment is outside this task. Limits and precise evidence are in [M2](../V02B_OPERATIONAL_OBSERVABILITY_M2.md).
