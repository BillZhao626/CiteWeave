# S-03 运行保障与评测

> M0 已执行：已验证不变量以 [M0 冻结范围](00_M0冻结范围.md) 为准，本文其余部分仍是完整目标设计。实测结果见 [M0 报告](../05_M0实测与选型结论.md)。

状态：目标规格，尚无新系统实测。只在列明环境和完整证据后才把目标改为已验收。

## 并发、超时与熔断

deadline 使用单调时钟，从服务接收请求算起，各下游只分配剩余预算。初值：在线 query 总 30 秒；检索含 query embedding 5 秒；rerank 2 秒；生成及一次格式修复共用剩余时间，至少保留 1 秒验证/落盘。数值用于首轮 GPU/API profile，CPU fallback 单独设 profile 和 SLO，不能把慢模式混入快模式分母。

provider 连接超时 3 秒、读取空闲超时 15 秒，并受总 deadline 限制；read timeout 不是总墙钟上限。可重试网络/429/5xx 最多额外 1 次、指数退避加抖动，尊重 Retry-After；超时含结果不确定时不盲目重发付费请求。客户端取消后不再启动新阶段；已在 GPU/远端执行的工作可能继续，要回收本地占用并记录状态。

初始单机配置：在线 query 执行槽 2–4，GPU 推理槽 1，摄取 worker 1，评测并发 1。等待队列有限；超限 429，不无限堆积内存。速率限制与并发限制分开；多 API 进程下不能只靠各自内存 semaphore 声称全局限流。

熔断按 provider/model/operation 分桶：连续 5 次可归因的依赖失败后 open 30 秒，half-open 只允许 1 个探测；成功关闭，失败再打开。用户参数错误/主动取消不计依赖故障。reranker 可降级；鉴权、数据隔离和证据合法性不可 fail open。阈值进入配置版本并用虚拟时钟测试。

## 任务可靠性合同

PostgreSQL transaction 写 job 与 outbox；publisher 周期发送消息，成功后标记。两步间退出允许重复投递。worker 获得 DB 执行 lease/token 后才增加 attempt；已完成的同任务直接返回持久结果，不重复写索引。

任务副作用使用确定性 chunk/upsert ID 和 snapshot job ownership。完成结果、状态与事件在 DB 事务落盘后才 ACK。任务运行中续租且带 fencing token，旧 worker 在恢复后不得覆盖新 worker 结果。Celery 的 result backend 不是业务完成真源。

显式配置 JSON serializer、acks_late、worker lost 行为、prefetch、hard/soft limits、visibility timeout。把长摄取拆成短可重放阶段；visibility timeout 大于阶段 hard deadline 加恢复余量，不能只无限增大以掩盖恢复慢。[Celery tasks](https://docs.celeryq.dev/en/stable/userguide/tasks.html)、[Redis broker caveats](https://docs.celeryq.dev/en/stable/getting-started/backends-and-brokers/redis.html)。

数据库补偿器扫描 outbox 未发、queued 超时、expired lease、cleanup_failed；可重试进入 retry_wait，超过次数进入 dead_letter 并可人工重放。取消采用持久 cancel_requested 标记，chunk 批次边界检测；取消后不再发布 snapshot。

生产 broker 单独实例、noeviction、持久化与备份；cache 可淘汰且可丢失。Redis/Valkey 丢失仍可根据 DB 状态恢复队列，但不承诺恢复未落盘的远端模型结果。下游不支持幂等时，副作用/费用“恰好一次”不可保证。

## 故障矩阵与验收

| 注入点 | 必须观察到的行为 |
|---|---|
| DB 已提交 job，broker 不可用 | job 可查询；outbox 稍后补发；重提同 key 不新增业务任务 |
| broker 已发布，outbox 标记前退出 | 可重复消息，最终一个有效 snapshot/结果 |
| worker 执行中被杀，换新身份重启 | lease 到期后被接管；旧执行不能覆盖新结果 |
| 完成事务成功，ACK 前退出 | 重投读取 completed，不重新执行副作用 |
| DB 完成事务失败 | 不 ACK，不返回已完成 |
| cache 丢失/不可用 | 可绕过缓存，安全与结果版本保持一致 |
| Qdrant 不可用 | 503 或显式允许的同版本降级；不访问其他库 |
| reranker 慢/OOM | deadline 后降级，worker/显存可恢复；无无限线程积累 |
| LLM 429/超时/格式错误 | 有限重试/修复；不超预算；状态可解释 |
| 删除 Qdrant 成功但对象存储失败，或反之 | tombstone 保持不可读；清理 job 重试，禁止假成功 |
| 发布与并发 query/rollback | 每个 run 只使用固定 release；没有混合版本 |
| 权限撤回后命中缓存/旧引用 | 授权仍拒绝读取 |

## 监控与复盘

结构化日志含 request_id/run_id/job_id/workspace_id、阶段、错误码、版本、耗时；不输出密钥、完整连接串或默认原文。公共 trace 只含脱敏摘要。OTel span 跨 API/worker/provider 传播，公开 API 返回 request_id 方便定位。[OpenTelemetry Python](https://opentelemetry.io/docs/languages/python/)。

指标：请求 P50/P95、错误率、超时率、活动/等待数、模型加载/推理耗时、显存峰值、Qdrant 延迟、job age/retry/DLQ、缓存命中、每 query tokens/成本。引用支持率属于评测指标，不随便从在线 self-judge 拼成业务 SLA。

日志默认 7 天、受控完整运行记录 30 天作为初值，可配置；原件按引用留存与用户删除策略管理。系统必须能解释“引用已删除/已撤权”，而不是永久保留被删除数据供回放。

## 备份与恢复

备份 PostgreSQL、原件/规范文本和 release 清单；Qdrant 做 snapshot 或按清单重建。备份需要同一逻辑版本点，单独 dump 数据库不保证与向量/原件一致。加密备份、记录 hash，恢复到新环境校验 KB 数/文档版本/引用跳转与权限。

个人单机初始目标：每日日备份，RPO≤24小时；在 1–2 万片段演示规模上恢复 RTO≤60分钟。两者是待演练目标；未演练不得写已保障。Compose 为单故障域，不承诺高可用、多可用区或 99.9% 在线率。

## 评测集与隔离

先自写 20–30 条 synthetic fixtures 用于逻辑测试；真实评测从许可已核查的至少两个公开领域建立 120 问初始集：60 dev、30 regression、30 sealed holdout。尽可能按文档族/版本分组，避免同一句或同一模板落在不同 split。120 条适合起步，分层样本过少时只报告计数，不宣传统计显著。

类型至少覆盖：单事实、跨段/表格、多方面、跨文档、冲突/版本、不可回答；中文为主并含英文，明确记下每类/语言/领域 n。每题包含 source revision、允许答案、必要事实、support spans、qrels、可回答性、标注者和争议状态。人评先双重核查 20–30 题，扩展时保存仲裁记录。

生产代码不能访问 qrels、case_id、split、gold answer；eval runner 把 query 与正常 API 一样提交。按 case ID 写分支属于泄漏。holdout 打开后转为固定回归集；不能在其上调完参仍叫未见测试集。

## 指标定义

| 指标 | 分母与计算 |
|---|---|
| Recall@k | 每题命中的相关 evidence/chunk 数 ÷ qrels 相关数；零相关题不混入，另报不可回答集 |
| MRR@k / nDCG@k | 首个相关排名 / 分级相关排序质量；固定 qrels 与 k |
| Final-evidence recall | 最终上下文中的必要支持片段覆盖；与 candidate recall 分开 |
| Citation identity validity | 可解析到当前授权版本的引用数 ÷ 全部输出引用数 |
| Quote exactness | 与规范原文一致的 quote 数 ÷ 全部输出 quote 数；零引用不能自动满分 |
| Citation support precision | 被证据支持的 claim–citation 边 ÷ 全部引用边，基于校准人评/Judge |
| Claim citation completeness | 有足够支持引用的可核验事实主张数 ÷ 所有可核验事实主张数 |
| Answer correctness | 必要事实与错误/矛盾标准下的人评/校准 Judge；不能只用 string match |
| Refusal precision/recall | 应拒答/实际拒答的混淆矩阵；同时报告错误拒答，防止全拒答刷分 |
| Performance/cost | 冷热缓存分开；P50/P95、有效并发、失败分母、tokens/真实计费与重试 |

Judge 先与人评校准，固定 rubric、模型、temperature、解析版本；同模型生成与 Judge 存在相关偏差。重要 A/B 可做双顺序判定，报告顺序一致性和缺失响应。所有请求（含失败/超时/空答案）进入运行分母，不选择性丢弃。

## 预注册质量目标（待 dev 校准）

硬门槛：关键权限/版本/未知引用失败为零；所有声称 quote_exact 的片段精确匹配；故障矩阵全部通过；没有 silent fallback 或未解释的丢失任务。

效果初始目标：真实可回答集 Recall@20≥0.80，引用支持 precision≥0.90，claim citation completeness≥0.85；不可回答集拒答 recall≥0.85，错误拒答率≤0.15。首次 dev 基线前可调整并注明原因；看过 sealed holdout 后不得为了宣布通过修改标准。它们不是当前成绩。

性能初始目标：在明确的 full-local GPU profile、1–2 万片段、query 并发 2、热模型/冷答案缓存条件下，检索加 rerank P95≤3秒，完整已验证回答 P95≤30秒。20 分钟负载验收使用受控 generator 替身；真实 API 小样本另报端到端网络波动，不用替身速度冒充真实回答速度。

对照实验顺序：dense-only、BM25-only、hybrid、hybrid+reranker、hybrid+reranker+evidence validation。先复用候选/嵌入跑免费检索消融，dev 选中后冻结候选再进行生成 A/B。配对 bootstrap 报区间、样本数与每类差异；样本太小就不宣称显著提升。

## CI 与开发纪律

PR：格式/类型/秘密与依赖扫描 → 核心单元/属性测试 → 真实 Postgres/Qdrant/broker 集成测试 → 前端关键 Playwright 流程。付费 LLM 评测不放每个 PR 自动运行；合并前/里程碑按预算跑受控子集，正式发布跑冻结协议。

TDD 用在 evidence ID/offset/权限、RRF、任务状态与版本切换等可明确定义的不变量。向量检索连真实 Qdrant 是集成测试；效果评估是独立评测，不能把 mock adapter 测试称向量召回已验证。

核心领域包 branch coverage≥85% 可作为发布目标，但同时规定关键失败窗口必须覆盖；总仓库覆盖率、测试数量、规范检查通过都不能替代真实质量/故障验收。低风险 UI 文案不必先写测试，引用跳转/上传/取消/鉴权 UI 属核心流程，必须有 E2E。
